What a Commit Actually Is

The atom of version control — and, not coincidentally, the atom of an audit trail.

Every other thing you will learn here — branches, pull requests, merges, reviews, history rewriting — is built out of commits. Get this one object right and the rest of Git stops being arbitrary. Get it wrong and every later concept feels like a rule you have to memorise.

This matters directly for your mission. In a governance or security role you are rarely the person writing the change. You are the person asking: what changed, when, by whom, under what approval, and can I prove it wasn't altered afterwards? A commit is the record that answers all five. Learning it as a compliance artifact — not just a developer's save button — is the fastest route from where you are to where you're going.

1. Git has three areas, not one

The single most common beginner confusion is believing a file lives in one place. It lives in three, and a change moves through them in order.

AreaWhat it holdsState of a file there
Working tree The actual files on your disk, as you see them in a text editor. Modified — changed, but Git has not been told to care yet.
Staging area
(a.k.a. the index)		 A list of exactly which changes go into the next commit. Staged — marked for inclusion, not yet recorded.
Git directory
(the .git folder)		 The permanent object database — every commit ever made. Committed — safely stored in the local database.

Two commands move a change rightwards along that table:

git add  <file>    # working tree  →  staging area
git commit         # staging area   →  git directory
The staging area is the part with no equivalent in Dropbox, Google Drive, or Save-As, which is why it feels strange at first. Its whole purpose is to let you commit part of what you changed. That is what makes a clean, reviewable history possible — and a clean history is the difference between an audit trail and a pile of files. Source: Pro Git, ch. 1.3.

2. A commit is a snapshot, not a list of edits

Most people assume Git stores "the changes" — the added and deleted lines. It doesn't. Pro Git is explicit: "Git thinks of its data more like a series of snapshots of a miniature filesystem." Each commit records the complete state of the project at that moment. Files that didn't change aren't stored twice; Git just keeps "a link to the previous identical file." [Pro Git 1.3]

The diffs you see on GitHub — green lines, red lines — are calculated on demand by comparing two snapshots. They are a view, not the stored data.

3. What's literally inside one

A commit object is tiny and plain-text. Here is a real one, as Git stores it:

tree d8329fc1cc938780ffdd9f94e0d364e0ea74f579
author Scott Chacon <schacon@gmail.com> 1243040974 -0700
committer Scott Chacon <schacon@gmail.com> 1243040974 -0700

First commit

Four things, and that's all there is:

  • tree — a pointer to the snapshot of every file and folder
  • parent — a pointer to the commit that came before (absent above, because this is the very first commit in the repository)
  • author and committer — who, and exactly when
  • the message — why

Source: Pro Git, ch. 10.2.

4. Why the history is tamper-evident

"Everything in Git is checksummed before it is stored and is then referred to by that checksum." A commit's name — that 40-character string like d8329fc… — is a hash of its own contents, and its contents include the parent's hash. [Pro Git 1.3]

The one thing to remember

Because each commit's identity is a hash of its content and of its parent's hash, you cannot quietly alter a past commit. Changing anything — one character of a file, one letter of a message, the timestamp — produces a different hash, which changes every commit after it. The tampering doesn't get blocked; it becomes visible.

That property is why version control is treated as evidence. It's the same chained-hash idea you already met in network security: integrity is proved by making change detectable rather than impossible.

Do this now

Ten minutes, in a throwaway folder you cannot break. Type the commands rather than pasting them — the motor memory is part of the point.

  1. Make a sandbox and turn it into a repository: 
    mkdir ~/git-sandbox && cd ~/git-sandbox
git init
  2. Create two files, so you have something to be selective about: 
    echo "keep this"    > wanted.txt
echo "not ready yet" > unwanted.txt
git status

    Both are listed as untracked. Both are sitting in the working tree.

  3. Stage only one of them, then look again: 
    git add wanted.txt
git status

    Now you can see the boundary: one file staged, one still only in the working tree. This is the three-area model on screen.

  4. Commit, with a message that says why: 
    git commit -m "Add the file that was ready"
  5. Read your own record back: 
    git log

    Note the hash, the author, the date, the message — the audit trail, in the order the fields appeared in section 3.

  6. Now look at the raw object. This is the payoff: 
    git cat-file -p HEAD

    You should see tree, author, committer, and your message — the exact shape from section 3, with no parent line, because it is your repository's first commit. Make a second commit and run it again: the parent line appears.

Check yourself

Answer before scrolling back up. Getting one wrong here is more useful than getting it right by re-reading — struggling to retrieve is what makes it stick.

What does a Git commit store?

  • A full snapshot of the project
  • A list of the line changes
  • A copy of the previous commit
  • A patch against the main branch

A snapshot. Git records the whole state of the project, reusing links to unchanged files. The red-and-green diff you see on GitHub is computed by comparing two snapshots — it is a view, not the stored data.

Where does git add move a change?

  • Into the staging area, awaiting commit
  • Into the commit history, becoming permanent
  • Into the working tree, becoming editable
  • Into the remote repository, becoming shared

Staging area only. git add marks a change for inclusion in the next commit; nothing is recorded in the object database until git commit runs, and nothing leaves your machine until git push runs.

Why can a past commit not be quietly edited?

  • Its hash covers its parent commit
  • Its author is verified by GitHub
  • Its message is stored on servers
  • Its files are locked after committing

The hash chain. A commit's name is a checksum of its contents, which include its parent's hash — so altering anything in the past changes every hash after it. Git does not prevent the edit; it makes the edit impossible to hide.

Three files are edited, but only one belongs in this change. What now?

  • Stage that one file, then commit
  • Commit everything, then revert others
  • Delete the others, then commit once
  • Push everything and sort it later

This is exactly what the staging area is for. git add wanted.txt then git commit — the other two changes stay in the working tree, untouched, waiting for their own commit. One commit, one complete idea.

Without looking: name Git's three areas, in the order a change passes through them, and the command that moves it between each.

Working tree → git add → staging area (index) → git commit → Git directory (.git, the object database). The matching file states are modified, staged, committed.
