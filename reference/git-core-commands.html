Core Git Commands

A one-page desk reference. Designed to be printed and kept next to the keyboard.

The model in one line

working tree  —git add→  staging area  —git commit→  local repository  —git push→  remote (GitHub)

Almost every command either moves a change one step along that line, or moves it one step back. When lost, run git status: it names where you are and usually suggests the next command.

Looking around

CommandWhat it tells you
git statusWhat is modified, what is staged, what branch you are on. Run it constantly — it is free and it is never wrong.
git logThe commit history, newest first: hash, author, date, message.
git log --onelineThe same history, one line per commit. The version you will actually use.
git show <hash>Everything about one commit, including the diff it introduced.
git diffChanges in the working tree that are not yet staged.
git diff --stagedChanges that are staged — i.e. a preview of your next commit.
git cat-file -p HEADThe raw commit object: tree, parent, author, committer, message.

Recording work

CommandEffect
git initTurn the current folder into a repository. Creates .git/.
git clone <url>Copy an existing remote repository, history and all, onto your machine.
git add <file>Stage one file's changes for the next commit.
git add .Stage everything changed below the current folder. Convenient; check git status first so nothing unintended rides along.
git commit -m "…"Record everything staged as one commit, with a message.
git pushSend local commits to the remote. Nothing is on GitHub until this runs.
git pullFetch the remote's new commits and merge them into your branch.

Undoing, by situation

The table people actually reach for. Find the sentence that matches your situation; do not improvise.

SituationCommand
I staged a file I didn't mean to. git restore --staged <file>
Unstages it. Your edits are kept.
I want to throw away my edits to a file. git restore <file>
Destructive. The edits are gone — they were never committed, so Git has no copy.
My last commit message is wrong. git commit --amend
Replaces the last commit with a new one. Safe before pushing; disruptive after.
I forgot to include a file in the last commit. git add <file> then git commit --amend --no-edit
A commit that is already pushed needs undoing. git revert <hash>
Adds a new commit that reverses the old one. Correct choice for shared history: the record stays intact, which is what an audit trail requires.
Note the distinction in that last row, because it is the one that separates people who understand Git from people who fear it. revert moves history forward to undo something and leaves the mistake visible. Commands that rewrite the past (--amend, reset, rebase) change hashes, which breaks everyone who already pulled — and erases evidence. On anything shared, prefer revert.

Anatomy of a commit

tree   d8329fc…    ← snapshot of every file and folder
parent a1b2c3d…    ← the commit before this one (absent on the first commit)
author Name <email> 1243040974 -0700   ← who wrote it, and when
committer Name <email> 1243040974 -0700   ← who applied it, and when

Commit message goes here

The commit's own 40-character hash is a checksum over all of the above. Since that includes the parent's hash, altering any past commit changes every hash that follows it — which is what makes the history tamper-evident.

Writing a commit message

RuleWhy
Say why, not what.The diff already shows what changed. Only you know the reason.
Imperative mood: "Add", "Fix", "Remove".Matches Git's own generated messages. Reads as an instruction the commit carries out.
One commit, one complete idea.Makes review possible, and makes a single change revertible on its own.
Short first line, then blank line, then detail.Tools display the first line alone. Anything past it must survive being truncated.
